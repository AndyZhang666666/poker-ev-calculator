# 假设清单

模型里每一个"凭空"的数字都在这里，标明来源与影响。

## 1. 手牌强度表（169 个值）

**来源**：任务书给出 27 个锚点，其余 142 个按规则生成（`scripts/gen-hand-strength.mjs`）：

- 口袋对：`60 + 4 × (点数 − 5)`，即 55 = 60 … KK = 92；AA 单独取 95
- 非同花：`高牌基准分 − 间隔惩罚`，高牌基准从 A=72 递减到 3=8，间隔惩罚按高牌档位分段
- 同花：同点数非同花 + 6
- 三个任务书锚点覆盖生成结果：72o = 5、73o = 6、82o = 7

**含义**：这是"可玩性"打分，不是对随机手牌的胜率。真实 hot-and-cold 胜率里 76s > 22，
本表相反（22 = 48 vs 76s = 27）—— 因为要满足任务书锚点 55 = 60。

**影响**：所有 EV 的绝对值都锚在这个尺度上。改动表值 = 改动全部结论，
所以 `npm run verify` 会断言 27 个锚点逐个相等。

## 2. 胜率修正（6 个常数）

| 项 | 值 | 依据 |
|---|---|---|
| 对手松 | +5pp | 松对手范围宽 → 我们的相对胜率高 |
| 对手紧 | −5pp | 范围窄 → 相对胜率低 |
| 对手下注 | −5pp | 下注是有牌的信号 |
| 对手加注 | −10pp | 加注是更强的信号 |
| 对手过牌 | +5pp | 过牌示弱 |
| 夹逼区间 | [5%, 95%] | 扑克里不存在 0% 和 100% |

**影响**：±5pp 是"一档"的量级。案例 6（99 vs 紧对手加注）在紧对手修正为 −5pp 时
跟注略优于加注；如果这个值改成 −15pp，最优决策会翻成弃牌。

## 3. 对手弃牌率（3 + 3 个常数）

```
foldRate = 基础弃牌率[对手类型] + (手牌强度 − 50)/200 + 行动修正[对手行动]
          再夹到 [10%, 70%]
```

| 对手类型 | 基础弃牌率 |
|---|---|
| 松 | 20% |
| 平衡 | 35% |
| 紧 | 50% |

行动修正：过牌 +10pp、下注 −5pp、加注 −15pp。

**已知的建模瑕疵**：`(手牌强度 − 50)/200` 这一项让"我方手牌越强 → 对手越容易弃牌"。
严格说对手看不到我们的牌，这个项在真实牌局里不成立。保留它的理由是任务书第 4.3 节的
原始公式就是这么写的，且它让"强牌加注"的直觉成立。代价是：手牌强度这个输入同时出现在
胜率和弃牌率两处，两个敏感度叠加，让手牌强度对加注 EV 的影响被放大。

实操上的表现：案例 5（KQs vs 松对手下注）弃牌率只有 24%，但因为胜率 68% 足够高，
加注仍然赢过跟注 —— 这条路径不依赖那个可疑项。而案例 3/6 需要靠"被跟注后胜率惩罚"
压住加注，见下一条。

## 4. 被跟注后胜率惩罚（3 + 3 个常数）

```
calledWinRate = clamp(winRate − 类型惩罚 − 行动惩罚, 5%, 95%)
```

| 对手类型 | 惩罚 |
|---|---|
| 松 | 5pp |
| 平衡 | 10pp |
| 紧 | 25pp |

行动惩罚：过牌 0、下注 4pp、加注 8pp。

**为什么需要这一项**：任务书原公式的加注 EV 直接用整体胜率算"被跟注"分支，
等价于假设对手跟注时的手牌分布和整体一样。这在紧对手身上严重失真 ——
紧对手愿意跟我们的加注，说明他手里基本是大牌。

**不加会怎样**：8 个案例里，案例 3（顺子听牌 vs 紧对手下注）和案例 6（99 vs 紧对手加注）
的最优决策会从"跟注"翻成"加注"，与任务书明确写的预期不符。
加进这一项后 8/8 命中。这是模型里最重要、也是唯一偏离任务书字面公式的地方。

**取值的依据**：25pp 这个量级来自一个手算 sanity check —— 一个被紧对手跟注的范围
大致收窄到 top 10%，对应的胜率降幅在 20–30pp 区间。不是拟合出来的。

## 5. 加注尺度

- 对手有下注：加注到 `对手下注 × 3`
- 对手过牌：改为下注 `2/3 底池`（案例 7：底池 300 → 下注 200）

**影响**：加注 EV 对尺度敏感。3 倍是个标准尺度，但不是最优尺度 —— 真实的 EV
应该在多个尺度里取最大。本工具没做这个优化，所以"加注 EV"可以被理解为
"按这个固定尺度加注的 EV"，不是"加注这个动作的最优 EV"。

## 6. 筹码与全押

- 跟注额 = `min(对手下注, 我方筹码)`
- 加注额 = `min(目标加注额, 我方筹码, 对手下注 + 对手剩余筹码)`
- 对手筹码为 0（已全押）时 `raiseAvailable = false`，加注从候选中移除

**影响**：案例 4（河牌顶对 vs 全押）因此没有加注 EV —— 这是对的，
对手已经全押就没有再加注的物理空间。

## 7. 明确不建模的东西

- 公共牌对强度的具体影响（只影响 UI 展示，不进入计算）
- 位置、人数、筹码深度以外的任何博弈因素
- 对手的历史频率、我方形象、牌桌动态
- 多条街的联合优化（每条街独立决策，不考虑"这手牌我打算打几条街"）
- 抽水

## 8. 确定性

没有随机数、没有蒙特卡洛、没有时间依赖（`generatedAt` 只到日期）。
同样的输入永远给同样的输出，所以 `results/cases.json` 可以字节级比对。
